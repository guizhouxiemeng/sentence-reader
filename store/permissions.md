# 权限理由

商店审核表单会逐条问"为什么需要这个权限"。
**这一段必须填，而且必须具体** —— 留空或写"用于提升用户体验"是最常见的被拒原因。

---

## `host_permissions`: `http://*/*`, `https://*/*`

**表单里填这段：**

```
阅读辅助的作用对象是「用户正在读的那篇文章」，而文章可能在任何网站上 ——
论文在出版商站点、预印本在 arXiv、课程材料在学校内网、技术文章在个人博客。
扩展无法预知用户会打开哪个网站，所以只能声明全部站点。

但声明不等于会读：

· 扩展不注册任何 content_scripts 自动注入规则。
  不点工具栏图标，它在任何页面上都不会运行。
· 只有用户主动点击图标（或从侧栏点「重新读取」）时，
  才通过 chrome.scripting.executeScript 把脚本注入到【当前那一个标签页】。
· 注入的脚本只做一件事：找出正文文字、按句切开、在原文上加高亮。
  它不读取表单、不读取 cookie、不读取与正文无关的 DOM。
· 扩展没有自己的服务器，读到的文字不会发送到任何我们控制的地址。

唯一的对外请求发生在用户主动按空格求助时：
把当前那一句发给【用户自己配置的】AI 服务。
如果用户选择默认的浏览器内置模型，内容完全不出本机。
```

---

## `scripting`

**表单里填这段：**

```
用于在用户指定的标签页里注入切句与高亮脚本
（chrome.scripting.executeScript）。

不声明静态 content_scripts，所以不存在"自动在所有页面运行"的情况。
注入是用户点击图标触发的，目标是当前标签页。
```

---

## `tabs`

**表单里填这段：**

```
两个用途：

① 判断当前标签页是否是「可读的网页」——
   遇到 chrome:// 、扩展页、新标签页时给出提示，而不是注入后失败。

② 侧栏场景下定位目标标签页。
   侧栏可能以独立标签页的形式打开，此时"当前活动标签页"未必是用户想读的那篇，
   需要列出候选标签页让用户明确指定（只读取标题和 URL）。

不读取标签页内容，不记录浏览历史。
```

---

## `activeTab`

**表单里填这段：**

```
用户点击工具栏图标时，临时获得当前页的访问权。
这是最小权限的做法：即使不申请 host_permissions，
点击图标这一个动作也能让扩展合法地处理当前页。

保留 host_permissions 是因为"记住上次读的文章、重新读取"这类操作
发生在点击之后，需要持续的访问权。
```

---

## `sidePanel`

**表单里填这段：**

```
讲解显示在浏览器侧栏里。

这是产品设计的一部分：用户需要一边看原文一边看讲解，
弹窗（popup）一点别处就关了，独立标签页又要来回切换。
侧栏是唯一能同时满足"不遮挡原文"和"不丢失"的位置。
```

---

## 没有申请的权限（可以主动说明）

**表单里如果有备注栏，建议补上这段：**

```
以下是同类扩展常见、但本扩展【没有】申请的权限：

· storage      —— 改用页面自身的 localStorage，避免把用户数据放进扩展存储
· history      —— 与阅读辅助无关
· bookmarks    —— 无关
· cookies      —— 无关，且不读取任何登录态
· webRequest   —— 不拦截、不修改任何网络请求
· downloads    —— 导出讲解用的是页面内 <a download>，不需要该权限

声明全部站点是功能所必需，不是权限囤积。
```

---

## 关于"全部站点"这个权限，如果审核要求收窄

**技术上可行的替代方案：**

```
改成只申请 activeTab，去掉 host_permissions。

代价：
· 每次重新打开侧栏都要再点一次图标（无法记住上次读的页面）
· PDF 支持会受影响（需要重新抓取文件）
```

**建议：先按现在的提交。** 如果被要求改，再改 —— 因为
"阅读辅助必须能用于任意文章"是这个产品的根本前提，
收窄之后产品价值会明显下降，值得先争取一次。
